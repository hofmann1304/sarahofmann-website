SPARQL: Fehlende Nachweise im Engineering Knowledge Graph finden

13. November 2026 · Verfasst von Sara Hofmann

Wie findet man technische Entscheidungen, denen ein Nachweis fehlt? In einem Knowledge Graph kann eine Abfrage genau diese Lücke sichtbar machen. Entscheidend ist, ob „kein Verweis vorhanden“ oder „kein passender Nachweis dokumentiert“ gemeint ist. Dieser Leitfaden zeigt drei ausführbare SPARQL-Abfragen und ihre unterschiedlichen Ergebnisse.

Der SHACL-Leitfaden behandelt Regeln für einen Review-Export. Hier geht es ergänzend um konkrete Arbeitslisten und die Frage, warum ein scheinbar vollständiger Bericht Lücken verdecken kann. Alle Daten und Kennungen sind frei erfundene Lehrbeispiele. Es werden keine Arbeitgeber- oder Kundendaten verwendet.

Vier Entscheidungen, drei verschiedene Lücken

Der Beispielexport enthält vier Entscheidungen im Zustand ex:ReadyForReview. Das eigene Vokabular ex: ist kein Industriestandard. Für diesen Versuch bedeutet ein passender Nachweis ausschließlich: eine über ex:evidence verknüpfte IRI mit der gespeicherten Aussage ex:passed true. Diese bewusst enge Regel ist keine technische Freigabe.

Den folgenden Block als decisions.ttl speichern. d1 hat zwei Quellen und einen als bestanden markierten Test. d2 hat keinen Nachweisverweis. d3 verweist auf einen als nicht bestanden markierten Test. Bei d4 steht statt einer Ressourcenkennung ein Textliteral.

@prefix ex: <https://example.org/engineering/> .

ex:d1 a ex:Decision ;
    ex:status ex:ReadyForReview ;
    ex:source ex:docA, ex:docB ;
    ex:evidence ex:testA .
ex:d2 a ex:Decision ;
    ex:status ex:ReadyForReview ;
    ex:source ex:docC .
ex:d3 a ex:Decision ;
    ex:status ex:ReadyForReview ;
    ex:source ex:docD ;
    ex:evidence ex:testB .
ex:d4 a ex:Decision ;
    ex:status ex:ReadyForReview ;
    ex:source ex:docE ;
    ex:evidence "test-C" .

ex:testA ex:passed true .
ex:testB ex:passed false .

Die Auswahl der Entscheidungen ist Teil des Prüfauftrags: Wir betrachten ausdrücklich klassifizierte Entscheidungen mit genau diesem gespeicherten Status. Ein Datensatz ohne Typ oder Status erscheint in den folgenden Arbeitslisten nicht. Vor der Auswertung sollte daher separat feststehen, welche Kennungen überhaupt erwartet werden.

Abfrage 1: kein Nachweisverweis vorhanden

FILTER NOT EXISTS prüft, ob das innere Muster für die aktuelle äußere Lösung keinen Treffer hat. Die Variable ?decision verbindet beide Teile. Maßgeblich ist SPARQL 1.1, Abschnitt 8.1.1 [1]. Die erste Abfrage als missing.rq speichern:

PREFIX ex: <https://example.org/engineering/>
SELECT DISTINCT ?decision
WHERE {
  ?decision a ex:Decision ;
            ex:status ex:ReadyForReview .
  FILTER NOT EXISTS { ?decision ex:evidence ?evidence . }
}
ORDER BY ?decision

Ergebnis: nur ex:d2. Für d3 existiert ein Verweis, obwohl der Test nicht bestanden ist. Auch das Literal bei d4 erfüllt das einfache Tripelmuster. Wer die Ergebnisliste „Entscheidungen ohne belastbare Evidenz“ nennt, verspricht deshalb mehr, als diese Abfrage prüft.

Meine Empfehlung ist eine präzise Bezeichnung im Bericht: „kein Nachweisverweis im geprüften Datenstand“. Diese Formulierung hält offen, ob der Nachweis an anderer Stelle existiert, noch nicht importiert wurde oder tatsächlich fehlt.

Abfrage 2: kein Nachweis nach der vereinbarten Regel

Die zweite Abfrage ergänzt die vereinbarten Bedingungen im inneren Muster. isIRI prüft die Art des RDF-Terms; es prüft weder die Erreichbarkeit noch die Richtigkeit einer Quelle. Die Funktionsdefinition steht in Abschnitt 17.4.2.1 [1]. Als qualified.rq speichern:

PREFIX ex: <https://example.org/engineering/>
SELECT DISTINCT ?decision
WHERE {
  ?decision a ex:Decision ;
            ex:status ex:ReadyForReview .
  FILTER NOT EXISTS {
    ?decision ex:evidence ?evidence .
    FILTER(isIRI(?evidence))
    ?evidence ex:passed true .
  }
}
ORDER BY ?decision

Ergebnis: ex:d2, ex:d3 und ex:d4. Die Liste fasst unterschiedliche Ursachen zusammen: kein Verweis, kein als bestanden dokumentierter Test oder ein ungeeigneter Werttyp. Für die Bearbeitung empfiehlt sich eine ergänzende Ursachenliste. Ein gemeinsames „nicht erfüllt“ reicht zum Filtern, aber noch nicht als Arbeitsanweisung.

Auch diese Regel hat eine klare Grenze. Ein veralteter oder unzutreffender Test mit ex:passed true genügt dem Muster. Die Aussage „bestanden“ wird hier gelesen, nicht nachgeprüft. Version, Anwendungsbereich und tatsächliche Prüfergebnisse gehören deshalb in die fachliche Bewertung. Welche zusätzliche Beziehung benötigt wird, ergibt sich aus der konkreten Engineering-Frage.

Abfrage 3: OPTIONAL erhält unvollständige Datensätze

Für eine Übersicht sollen Entscheidungen auch dann erscheinen, wenn Zusatzangaben fehlen. OPTIONAL kann vorhandene Bindungen ergänzen und lässt die äußere Lösung bei einem fehlenden optionalen Treffer bestehen. Das beschreibt Abschnitt 6 [1]. Als report.rq speichern:

PREFIX ex: <https://example.org/engineering/>
SELECT ?decision ?source ?evidence
WHERE {
  ?decision a ex:Decision ;
            ex:status ex:ReadyForReview .
  OPTIONAL { ?decision ex:source ?source . }
  OPTIONAL { ?decision ex:evidence ?evidence . }
}
ORDER BY ?decision ?source ?evidence

Ergebnis: fünf Zeilen für vier Entscheidungen. d1 erscheint wegen seiner beiden Quellen zweimal. Die Nachweisvariable bleibt bei d2 ungebunden. Würden beide optionalen Tripelmuster als Pflichtmuster geschrieben, verschwände gerade dieser problematische Datensatz aus dem Bericht.

Zählen Sie daher nicht ungeprüft Ergebniszeilen als Entscheidungen. Für eine Liste eindeutiger Kennungen genügt hier eine Projektion SELECT DISTINCT ?decision. Wenn Quelle und Nachweis mit ausgegeben werden, bleiben die unterschiedlichen Kombinationen auch mit DISTINCT verschieden. Die Regeln zur Duplikateliminierung stehen in Abschnitt 15.3 [1].

Eine weitere typische Falle ist ein Filter auf einer optional gebundenen Variable außerhalb des optionalen Blocks. Dadurch können Lösungen mit fehlendem Wert entfallen. Ob der Filter in den Block gehört oder die Entscheidung bewusst ausschließen soll, muss aus der Berichtsfrage hervorgehen. Diese Varianten nicht ohne Gegenprobe austauschen.

Lokal mit Python und RDFLib ausführen

Die vier Dateien in einem eigenen Arbeitsordner ablegen. Benötigt werden Python und RDFLib; geprüft wurde das Beispiel mit Python 3.14 und RDFLib 7.6.0. Die Bibliothek in einer separaten Umgebung mit python -m pip install rdflib==7.6.0 installieren. Folgenden Block als query_decisions.py speichern und dort python query_decisions.py ausführen:

from pathlib import Path
from rdflib import Graph

graph = Graph().parse("decisions.ttl", format="turtle")
for name in ("missing", "qualified", "report"):
    query = Path(name + ".rq").read_text(encoding="utf-8")
    print(name)
    for row in graph.query(query):
        print(tuple(None if value is None else str(value)
                    for value in row))

Das Skript liest ausschließlich die angegebenen lokalen Dateien und verwendet keine entfernten SPARQL-Dienste. Es verändert den Graphen nicht. RDFLib führt die Abfragen über Graph.query() aus; die Iteration liefert die Variablenwerte je Ergebniszeile. Siehe die offizielle RDFLib-Dokumentation [2]. Fehlende Bindungen werden im Beispiel ausdrücklich als None ausgegeben.

Gegenproben vor dem Einsatz

  1. Nachweis ergänzen: d2 mit ex:testA verknüpfen. Die Entscheidung muss aus beiden Fehlerlisten verschwinden.
  2. Nur einen zweiten Quellenverweis ergänzen: Die Fehlerlisten dürfen sich nicht ändern; die Übersicht erhält eine zusätzliche Kombination.
  3. Typ einer Entscheidung entfernen: Sie verschwindet aus der gewählten Grundmenge. Das demonstriert eine Auswahlgrenze, keine erfolgreiche Reparatur.
  4. Leeren Graphen abfragen: Keine Treffer bedeuten hier keine geprüften Entscheidungen. Erwartete Kennungen müssen deshalb zusätzlich abgeglichen werden.

Diese Gegenproben wurden automatisiert am Lehrbeispiel ausgeführt. Für einen produktiven Bericht sollten Datenstand, Abfrageversion, betrachteter Graph und erwartete Grundmenge dokumentiert werden. Bei mehreren benannten Graphen ist zusätzlich festzulegen, aus welchem Graphen Entscheidungen und Nachweise gelesen werden. Eine Suche im falschen Datenbereich kann sonst wie eine fachliche Lücke aussehen.

Wie ergänzen sich SPARQL und SHACL?

Für diesen Arbeitsablauf empfehle ich SPARQL für gezielte Fragen und nachvollziehbare Arbeitslisten, SHACL für einen vereinbarten Strukturvertrag. Beide benötigen fachlich definierte Regeln und eine überprüfte Datenauswahl. Der Einstieg zu Knowledge Graphs in der Bildverarbeitung zeigt, wie Entscheidungen, Konfigurationen und Evidenz zusammenhängen können.
